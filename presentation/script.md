# 발표 스크립트 (16장, 목표 10~11분)

각 슬라이드 제목 아래 괄호는 목표 소요 시간. 대본은 그대로 읽기보다 흐름 참고용으로 쓴다.

---

## 1. 제목 (15초)

안녕하세요. 이커머스 행동 로그를 Iceberg 기반 Lakehouse로 처리하는 파이프라인을 발표하겠습니다.
Kafka로 이벤트를 재생하고, Flink로 Bronze에 적재하고, Spark와 Iceberg로 Silver·Gold를 만들어
Athena·Superset에서 조회하는 구조입니다.

## 2. 핵심 문제 (40초)

이 프로젝트의 핵심 문제부터 짚고 가겠습니다. 지연 도착 이벤트와 세션을 넘는 구매가
이미 계산해둔 과거 결과를 바꾼다는 점입니다. 예를 들어 늦게 도착한 view나 cart 이벤트는
기존 퍼널의 최초 시각과 집계값을 바꿀 수 있고, 새로운 purchase는 같은 사용자가 과거
다른 세션에서 봤던 상품의 전환 여부까지 바꿀 수 있습니다. 매번 전체를 다시 계산하면
정확하긴 하지만 데이터가 커질수록 비용이 감당이 안 됩니다. 그래서 영향받는 키만 골라
재계산 범위를 줄이고, Iceberg의 원자적 갱신으로 안전하게 반영하는 방식을 택했습니다.

## 3. 데이터 규모·KPI (35초)

데이터는 Kaggle의 이커머스 행동 로그 데이터셋이고, 전체 7개월 2.85억 건 중 2019년 10월
4,245만 건을 기본으로 씁니다. GMV, 퍼널 전환율, Cart 이탈률, 카테고리 GMV, 운영 품질
이렇게 다섯 가지를 핵심 KPI로 잡았고, 원본에 order_id나 quantity가 없어서 구매 건수
대신 purchase 이벤트 수로 표기한다는 점만 짚고 넘어가겠습니다.

## 4. 전체 아키텍처 (45초)

전체 구조입니다. Kafka에서 Flink로, Flink가 S3 Bronze에 원본을 그대로 쌓고,
Spark가 Iceberg로 Silver를 정제한 다음 영향받은 날짜만 Gold로 재집계합니다.
Airflow가 이 전체 흐름을 스케줄링·재시도하고 spark_pool로 직렬화하고요,
Prometheus·Grafana는 Kafka·Flink 상태를 실시간으로 감시합니다.

## 5. Superset — 비즈니스 KPI와 배치 품질 (30초)

Superset은 두 갈래로 나눠뒀습니다. 왼쪽은 커밋된 Gold 기준 비즈니스 KPI,
오른쪽은 일별 데이터·Iceberg 품질입니다. 둘 다 같은 조회 기간 기준으로 봐서
"이 기간의 숫자가 이 기간의 파이프라인 상태에서 나온 게 맞다"는 걸 같이 확인할 수 있게 했습니다.

## 6. Grafana — 스트리밍 상태와 즉시 알림 (40초)

Grafana는 반대로 배치 커밋을 기다리지 않는 즉시 신호 담당입니다. Kafka consumer lag,
Flink RUNNING 잡 수, checkpoint 실패 여부뿐 아니라 정상 이벤트 유입이 끊기는 것까지
실시간으로 보고, 임계값을 지속적으로 벗어나면 Slack으로 알림이 갑니다. Airflow
태스크가 재시도를 다 소진하고 최종 실패하는 경우도 Slack으로 알리는데, 이건 Grafana
경로가 아니라 Airflow 콜백이 webhook을 직접 호출하는 별도 경로입니다. 아래쪽에 있는
실시간 잠정 비즈니스 KPI는 뒤에서 다시 설명하겠습니다.

## 7. 메달리온 계층 (35초)

Bronze는 이벤트 1건 grain의 원본 보존, Silver는 정제된 이벤트와
(user_session, product_id) 단위 퍼널, Gold는 일 단위 집계 5개 테이블입니다.
GMV는 이벤트 grain인 silver_events에서, 전환율은 퍼널 grain인 silver_funnel에서
계산하고 이 둘을 절대 섞지 않는다는 게 원칙입니다.

## 8. Cross-session 전환 (40초)

같은 사용자가 한 세션에서 상품을 보기만 하고, 며칠 뒤 다른 세션에서 그 상품을 사면
과거 세션의 퍼널에도 전환을 표시해줍니다. 이걸 얼마나 넓게 볼지가 관건인데,
7일로 보면 34만 건, 30일로 보면 39만 건 넘게 잡힙니다. 다만 저희가 가진 데이터가
31일치뿐이라 Cart 이탈률은 상한으로, 지연 전환 수는 관측 가능한 하한으로 해석해야 합니다.

## 9. 트러블슈팅 1 — 잘못된 Gold 집계 기준 (50초)

여기서부터 실제 겪은 문제 세 가지를 다루겠습니다. 첫 번째는 집계 기준을 잘못 잡았던
경험입니다. Funnel 테이블에서 GMV를 계산했더니 반복 구매가 접혀서 7.1% 과소집계됐고,
purchases 나누기 carts로 전환율을 냈더니 cart를 거치지 않은 구매까지 섞여서 110%가
나왔습니다. category NULL 처리도 순서를 잘못 잡아서 결측 34%가 전부 ALL로 잡혔고요.
근본 원인은 이벤트 grain과 퍼널 grain을 섞은 것, 그리고 분자가 분모의 부분집합이
아니었던 겁니다. GMV는 이벤트 테이블에서, 전환율은 carted=1 AND purchased=1
기준으로 다시 잡고, NULL은 unknown으로 바꾼 뒤 grouping()으로 ALL을 구분해서 해결했습니다.

## 10. 트러블슈팅 2 — MOR 무조건 UPDATE로 파일 폭증 (55초)

두 번째는 Iceberg MOR 전환 후 겪은 문제입니다. 똑같은 배치를 두 번 처리해봤는데
결과 행 수나 KPI는 똑같았지만, silver_funnel의 data file이 31개에서 83개로,
position delete file이 0개에서 52개로 늘어났습니다. 원인은 updated_at 컬럼이
매번 현재 시각으로 찍히다 보니, MERGE의 UPDATE SET * 조건이 실제 데이터가 같아도
전부 갱신 대상으로 잡은 겁니다. MOR은 갱신될 때마다 기존 행을 delete file로 표시하고
새 행을 쓰기 때문에 파일이 계속 늘어난 거고요. updated_at을 제외한 실제 컬럼이
바뀌었을 때만 UPDATE하도록 고쳐서 해결했고, 이미 쌓인 파일은 compaction으로
83개에서 31개로 다시 정리했습니다.

## 11. 트러블슈팅 3 — PyFlink 커스텀 지표의 타입 제약 (45초)

세 번째는 오늘 실시간 KPI를 만들다 바로 겪은 문제입니다. purchase 금액 누적값을
Prometheus Counter로 노출하려고 했는데, PyFlink의 Counter·Gauge가 전부 정수만
받다 보니 소수점 있는 금액을 그대로 못 넣었습니다. 원본에 통화가 없어서 단위를
가정할 수도 없었고요. 그래서 금액을 100배 정수로 스케일링해서 Counter에 담고,
Grafana 쿼리에서 다시 100으로 나누는 방식으로 우회했습니다. 이때 float 대신
Decimal로 변환해서 반올림 오차도 없앴습니다. 이렇게 만든 지표를 같은 시간대
Bronze 실제 적재량과 대조해봤는데 view, cart, purchase 건수와 금액 합계가
전부 정확히 일치하는 걸 확인했습니다.

## 12. Bronze는 plain Parquet, Silver·Gold는 Iceberg (40초)

이제 기술 선택 근거로 넘어가겠습니다. Kafka나 Airflow처럼 흔한 선택은 생략하고
설명이 필요한 것만 다루겠습니다. 먼저 Bronze는 plain Parquet, Silver·Gold는
Iceberg로 나눈 이유입니다. Bronze는 원본을 그대로 쌓기만 하면 되니 갱신 기능이
필요 없지만, Silver·Gold는 지연 도착 때문에 과거 결과가 계속 바뀌니까 MERGE와
원자적 파티션 교체, snapshot이 필요합니다. 전 계층을 plain Parquet로 갔다면
갱신·원자성을 직접 구현해야 했을 거고, Bronze까지 Iceberg로 갔다면 지금 수준의
단순 수집에 비해 카탈로그 복잡도가 과했을 겁니다.

## 13. 영향 키 기반 퍼널 재계산 (40초)

두 번째는 영향 키 기반 재계산입니다. 전체 재구축은 정확하지만 데이터가 커질수록
비용이 큽니다. 그래서 이번 배치에서 바뀐 직접 영향 키와, 새 구매가 과거 30일
퍼널에 미치는 전파 영향 키, 이 두 개만 합쳐서 재계산합니다. 이 방식이 맞는지
검증하려고 증분 결과와 전체 재구축 결과를 비교해봤는데, 1,342만 행에서
양방향 차집합이 0건으로 완전히 일치했습니다.

## 14. Silver MOR · Gold COW 혼용 (40초)

세 번째는 Silver는 MOR, Gold는 COW로 다르게 가져간 이유입니다. 실측해보니
컬럼 하나만 바꿔도 COW는 133만 행, 100MB 넘게 재작성해야 했고, 파티션
가지치기 효과는 하루치가 전체 31일치보다 34배 작았습니다. Silver는 증분
MERGE가 30일 범위까지 건드릴 수 있어서 MOR로 재작성 부담을 낮췄고, Gold는
영향 날짜를 통째로 overwrite하니까 row-level delete의 이점이 작아서 COW를
그대로 유지했습니다.

## 15. Flink 선택 이유와 실시간 KPI (55초)

마지막 기술 선택은 Flink입니다. 단순히 "실시간이니까 Flink"가 아니라,
Spark는 정합성이 중요한 배치 재계산을, Flink는 Kafka 이벤트의 지속적인 수집과
즉시 관측을 담당하는 역할 분리입니다. Kafka 이벤트를 끊김 없이 소비하면서
checkpoint로 offset을 복구하고, topic별로 독립적으로 처리하면서 parallelism을
늘릴 수 있고, backpressure나 checkpoint 상태를 Grafana로 바로 볼 수 있다는 게
장점입니다. 여기에 입력 계약을 검증하는 역할도 추가했는데, 계약을 지킨 정상
이벤트는 Bronze로, 위반한 이벤트는 사유를 붙여 DLQ 토픽으로 보냅니다. 그리고
실시간 잠정 KPI, 그러니까 이벤트 유입량과 purchase 건수·금액을 같은 job에서
같이 뽑아내는 기능도 추가했고, 앞서 본 것처럼 Bronze 실측과 정확히 일치함을
검증했습니다. 다만 재처리나 30일 전환 창이 반영 안 되니 확정 GMV가 아니라
운영 신호로만 쓴다는 점은 분명히 하고 있습니다.

## 16. 개선 계획 (30초)

앞으로 할 일은 세 가지입니다. 현재 구현한 DLQ에 발생량 알림과 재처리 절차를
추가하겠습니다. Producer가 늘어 메시지 계약 관리가 복잡해지면 JSON에서 Avro와
Schema Registry로의 전환을 검토하겠습니다. 마지막으로 실제 관측 데이터를 바탕으로
Iceberg 유지보수 주기와 운영 알림 임계값을 조정하겠습니다. 여기까지입니다.
질문 받겠습니다.
